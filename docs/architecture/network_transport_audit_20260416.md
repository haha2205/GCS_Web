# Apollo GCS 网络传输审计

日期：2026-04-16

## 结论

当前项目在“高频遥测接入不应被前端/WebSocket/录制拖死”这一点上，整体方向是正确的，已经满足基本的实时系统解耦要求：

- UDP 接收回调保持轻量，主处理在后台队列中完成。
- 前端刷新不会中断 UDP 接收链路。
- WebSocket 慢连接不会直接反压到 UDP 接收路径。
- 录制、在线分析都已经从主接收路径中拆分出去。

但如果按“网络数据传输完整性与可观测性”的更严格要求来看，仍有几个明显问题需要注意：

1. 协议校验失败后仍继续解析，这不符合数据完整性要求。
2. 解析失败时部分消息会填充默认值继续向后流转，这会把“坏包”变成“假数据”。
3. 现有 `data_quality_report.json` 的 `total_bytes` 是“解码后存储字节”，不是“线上网络字节”，不能直接拿来做码率判断。
4. 上行命令发送端仍存在源端口回退逻辑，协议一致性不够严格。

## 2026-04-16 当日晚些时候的落实

本次已完成两项收口：

1. 协议解析器当前只对真正无法继续解析的情况做拒收，例如缓冲溢出、payload 提取失败、结构体解码失败；对于 `checksum` 异常、已知 payload 长度偏差等现象，当前改为记录为 `parser_issues` 供运行时观测，不做严格拦截。
2. 后端已新增运行时流量统计出口：
  - `GET /health` 中新增 `traffic`
  - `GET /api/traffic/stats` 提供独立统计视图
3. 已开始在后端内部引入一层 `standard_event`，作为协议消息和下游消费之间的标准事件包络，当前挂载在 WebSocket/在线分析出口，不写入原始录制消息。
4. OnlineAnalysis 转发链当前优先按 `standard_event.routing_key / event_type / sequence` 进行路由和消费，同时仍保留原始 `data` 以兼容旧接口。

当前统计分为四层：

- `rx_datagrams`：UDP 原始收包层
- `parsed_messages`：协议解析成功后的业务报文层
- `tx_packets`：后端上行发送层
- `parser_rejections`：协议层拒包统计
- `parser_issues`：协议层非阻断异常观测

这意味着现在既能看“线上实际流量”，也能看“协议层丢掉了多少坏包”。

## 当前链路是否符合基本网络传输要求

### 符合的部分

- 多端口监听明确：主聚合接收 `30509`，兼容飞控遥测 `18506`，规划 `18511`，雷达 `18507`。
- 每个 UDP 端口各自维护独立解析器缓冲区，避免多端口数据串扰。
- UDP 接收缓冲区显式增大到 `4 MiB`，有助于降低高频场景下的 socket 丢包概率。
- 主处理链路使用有界队列：
  - `packet_processing_queue = 2048`
  - `recording_queue = 8192`
  - `online_analysis_queue = 256`
- 高频消息满队列时采用“按类型只保留最新值”的合并策略，而不是无限堆积。
- WebSocket 广播是并发发送，并带 `0.25s` 发送超时，断开连接会被清理，不会长期占住发送路径。
- 前端刷新仅影响 WebSocket 连接，不影响 UDP server、解析器、录制、后台队列。
- 上行命令有基本节流控制和重复发送机制，避免同一通道无节制地并发发送。

### 不符合或存在风险的部分

#### 1. 校验和错误仍继续解析

协议解析器在校验和不匹配时仅打印 warning，不丢弃报文。这意味着损坏帧仍可能进入：

- 前端显示
- 录制文件
- 在线分析

这不符合“校验失败即视为无效数据”的基本网络完整性原则。

#### 2. 解析失败时使用截断/补零默认值继续下游传播

部分飞控结构体在解析失败后，会对 payload 截断或补零后继续生成结果。这会让下游看到“看起来合法但实际失真”的业务数据，不利于故障定位，也会污染统计和录制。

#### 3. 当前 `data_quality_report.json` 不是网络码率统计

`data_quality_report.json` 中的 `msg_size`、`total_bytes`，统计的是：

- `json.dumps(decoded_data)` 之后的 UTF-8 字节数

也就是“解码后 JSON 存储体积”，不是：

- UDP payload 原始字节数
- UDP frame 实际线上字节数

因此：

- 它适合衡量录制/存储压力
- 不适合直接衡量网络码率

#### 4. 上行源端口仍有回退逻辑

发送时优先使用固定源端口 `18506`，但如果对应 transport 不可用，会回退到 `listen_port`，最后甚至回退到任意 transport。这意味着上行源端口在异常状态下不稳定，可能影响对端按固定源端口建立的协议假设。

#### 5. 命令限流提示文字与实际常量不一致

代码提示“至少间隔 100ms”，但当前常量是 `0.5s`。这不是链路级大问题，但会误导上层对发送频率的判断。

## 对前端链路的影响

当前架构下，前端刷新不应导致后端 UDP 链路中断，原因是：

- UDP 监听器和 WebSocket 管理器生命周期独立
- 前端刷新只会断开浏览器 WebSocket
- 后端仍继续收包、解析、排队、录制
- 前端重连后会收到缓存快照

因此，如果前端出现“卡顿”，更可能来自以下两类原因：

1. 前端渲染层压力过大，而不是后端网络链路中断。
2. 后端队列正在合并高频消息，导致前端看到的是“最新值降采样”，而不是每一帧原样到达。

## 建议的后续改进

1. 校验和错误时直接丢包，不再继续解析。
2. 结构体解析失败时，标记报文无效并停止向前端/录制传播，不要补零构造假数据。
3. 在录制与质量报告中新增两套统计字段：
   - `wire_payload_bytes`
   - `wire_frame_bytes`
4. 为 UDP 下行增加丢包/乱序观测字段；如果协议中没有序号，建议补充业务序号。
5. 固化上行源端口，不再回退到任意 transport。
6. 修正命令限流提示文字，使其与真实常量一致。
